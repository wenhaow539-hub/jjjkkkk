1. **Playwright 无法附着 CDP（阻塞级，已解除）**
   - 现象：`connect_over_cdp('http://127.0.0.1:9222')` 卡死直到超时，协议日志只到 `<ws connected>`。
   - 根因：**只要浏览器里存在任意 1 个"渲染线程卡死"的标签页，Playwright 的 attach 就永远返回不了**（它必须把所有已存在页面初始化完）。

   - 影响面：`core/browser.py`、`CrawlerRunner` 的 browser-cdp 模式、以及拟建的 dual_browser_scheduler 全部受影响。**建议在 attach 前加"探测并关闭无响应标签页"的前置清理。**

2. **爱企查有 CDP 反调试检测（页面级 JS）**

## 验证码风险加固（用户看到百度安全验证页后追加）

用户截图显示 `wappass.baidu.com/static/captcha/tuxing_v2.html`，其 **`backurl=https://www.aiqicha.com/s?q=...`**

（该域会直接跳百度验证码），所以这次验证码很可能是我那次探测触发的，与 enricher 主路径无关。

### 修掉的两个防护缺口
1. **验证码被开在另一个标签页时完全检测不到**：原 `_detect_antibot_page` 只看当前页，
   而实际场景是「验证码另开一个标签页 + 原页面留空白」→ 会被判成 `no_result_cards`，
   而它属于 BENIGN（不计熔断）→ 熔断永远不触发，会继续空转烧请求。
   → 新增 `_find_captcha_page(page)`：扫描整个 context（URL 含 `wappass.baidu.com`/`/captcha/`/`verify`
   且标题或正文含 安全验证/滑动验证/旋转图片/请输入验证码），命中则打印指引并等待人工
   （最多 captcha_timeout 秒）；通过则继续，超时则 `blocked=True` + `last_error=captcha_other_tab`。
2. **`no_result_cards` 被错当成良性**：enricher 已能识别「暂无数据/没有找到」并回 `company_not_found`，
   所以等到超时都无卡片也无提示 = 页面根本没渲染（多为被拦）。→ `BENIGN_ERRORS` 收窄为
   `{company_not_found, name_too_short}`；`_classify_result` 判定顺序改为
   「异常 → blocked/captcha → **有数据=ok** → 良性查无 → 其它错误=failed」。

## 「独立站又全空了」根因：Cookie 头过大导致 GS 全部 400（已修）

### 现象与证据
2026-09-16 11:42 那次 `--pipeline`（keyword=bag, 10 家）：
- 日志里**每一个** GS 详情请求都是 `⚠️ [GS] 详情页抓取失败(HTTP 400)`
- 结果：独立站、GS 中文工商名、注册地址**三列全空**（表里 10 行独立站非空=0）
- 用户并未改过 GS 代码 —— 所以看起来像"又坏了"

### 根因（一次对照实验定性）
`crawlers/globalsources.py` 里 `raw_cookies = await context.cookies()` **没有域名过滤**，
把浏览器里**所有域**的 cookie 都塞给了 GS 子域：

```
上下文共 276 条 cookie：.globalsources.com 27 / .alibaba.com 17 / .divoom.com 17 /
.made-in-china.com 14 / www.aiqicha.com 13 / .tianyancha.com 11 / aiqicha.baidu.com 9 / .baidu.com 8 …
拼成 Cookie 头 = 16,454 字节

全部 cookie（旧逻辑） -> HTTP 400  <title>400 Request Header Or Cookie Too Large</title>
仅 GS cookie（新逻辑） -> HTTP 200  90,975 字节
不带 cookie           -> HTTP 200  90,976 字节
```

**为什么突然坏**：这个 9222 浏览器今天被逛过爱企查/百度/企查查/天眼查，cookie 数量越过 GS 上限。
代码一直有这个问题，只是以前 cookie 少没触发。

### 修复
1. `crawlers/globalsources.py`：`await context.cookies("https://www.globalsources.com")` 并按 domain 含
   `globalsources.com` 过滤；加 `COOKIE_HEADER_LIMIT = 6000` 兜底（过滤后仍超限则本次不带 cookie，
   实测不带也 200）；日志 DEBUG 打印实际条数与字节数。
2. `_fetch_html`：400 时把服务端原话带进告警
   （`HTTP 400(Request Header Or Cookie Too Large → Cookie 头过大)`），不再只说"HTTP 400"。

### 同时发现旧脚本"自我暴露"

1. **绝不触碰页面对象**：非原始值一律替换为占位符 `'[object]'`（只用 `typeof` 判断，

## 验证码调研：轮换验证码（百度 tuxing_v2）有没有开源方案

用户反馈：**约每 15 家企业就弹一次图像验证码**（`wappass.baidu.com/static/captcha/tuxing_v2.html`，
"拖动左侧滑块使图片为正" = 旋转/角度类验证码）。

### 结论：开源项目有，但**解出角度只是三件事之一**
1. **角度识别**（开源可解）：
   - `rotate-captcha-crack`（原作者 Starry-OvO，多个 fork：V1ammer / Lancger / mwhwe）
     用 CNN 预测旋转角度，模型 RotNet(ResNet50) / RotNetR(RegNet_Y_3_2GF)，
     **跨域测试集就是用百度验证码做的**，预训练模型在 Releases，可起 HTTP 服务
     （`POST 图片 → {"pred": 角度}`）；部分 fork 报 1.3° 误差（街景数据训练）。
     依赖 PyTorch，CPU 可跑（慢）。
   - `ddddocr`：轻量（120ms/张、简单码 96%），有 `slide_match`（滑块缺口定位），
     但**不支持旋转校验**（社区确认）。
   - 百度现在的旋转图多为 **AI 生成、每张不重复** → 模板/直方图匹配类方法失效，必须用角度预测模型。
2. **参数加密**（要自己逆）：`viewlog` 拿 as/tk → `getstyle` 拿 backstr →
   `ac_c = round(angle * 212 / 360, 2)`（滑块最大位移 212px）→ `rzData`（含轨迹）经 **AES-ECB** 加密成 `fs`。
3. **轨迹模拟 + 环境检测对抗**：`rzData` 里含拖动轨迹；还有 `spin-0` 动态 p 值（SHA1）用于环境检测。

→ 即：**角度识别开源能解决，但后两项要自己逆向、且站点一改就失效**。属于军备竞赛。

### 按性价比的现实建议（推荐顺序）
1. **人工滑一下**（当前最优）：验证码页已能跨标签页识别 + 等待 60s；每滑一次约解锁 15 家，人工 10~20 秒。
2. **账号/IP 轮换**（第 1 项，结构性解法）：4 账号 ≈ 把"15 家一次验证码"摊成 4 倍体量。
3. **付费打码平台 API**（要自动化时最省事）：旋转类有现成接口（返回角度），成功率高于自建。
4. **自建 rotate-captcha-crack**：可行但要接受"模型误差 + 自己补轨迹/加密 + 随时失效"。

### 当前代码在验证码上的行为（可调）
- 检测到验证码 → 打印提示并**等 60s**（`captcha_timeout`）；通过则继续，超时记 `captcha_timeout` 并 **blocked=True**。
- 注意：**单次验证码不会触发熔断**（`_classify_result` 只看连续 3 家 failed），所以无人值守时会白等 60s 后继续跑。
  → 可加 `--captcha-wait 0`（快速失败，不空等）供无人值守场景。

## 付费打码平台接入（用户选 C 项，已实施）

### 核心判断：**拖动的加密参数不需要逆向**
百度旋转验证码提交时带的 `fs`（`rzData` 经 AES-ECB）、`spin-0` 动态 p、`fuid` 环境指纹，
**都不需要我们构造** —— 因为拖动是**在真实浏览器里用真实鼠标事件**（CDP `Input.dispatchMouseEvent`）
完成的，页面自己的 JS 会采集轨迹并生成这些加密值。
我们要做的只有三件：**取图 → 问平台"转正多少度" → 按 `角度/360×轨道宽度` 拖到位**。
（这条判断把"军备竞赛级逆向"降级成"一次 HTTP 调用 + 一次拟人拖动"。）

### 新增 `enrichers/captcha_solver.py`（两家协议已核实，勿凭记忆改）

### 实施中修掉的 4 个真缺陷（都是实测挖出来的，不是预想）
1. **重试超程**：原按"距离"硬拖，第二轮从滑块**当前位置**又拖了一整个角度距离 →
   落点 175px ≠ 目标 66px。滑块起始位置未必在轨道最左端（失败重试时可能没归零）。
   → 改为**按增量拖**：`_slider_geometry()` 量出 `travel` 与当前 `offset`，只拖 `目标偏移 - 当前偏移`；
   增量≈0 时按住即松，不空拖。
2. **`len(body) > 512` 当图片校验是错的**：纯色小图压缩后不到 300 字节被误杀，
   而 HTML 错误页几 KB 反而能过关 → 改为 `_looks_like_image()` **魔术字节**校验
   （PNG/JPEG/GIF/WebP/BMP 头）。
3. **`_captcha_present` 把验证码图片也算作"仍需处理"**：验证通过后图片元素可能仍留在页面上
   （只有滑块/容器消失）→ 人工等待会误判成"还没过"而白等到超时。**这是本次我自己引入的回归**，
   已把 `img.passMod_spin-background` 从判定里去掉（判断依据只看**可交互控件**）。
4. **`.env.example` 推荐的 `CAPTCHA_PROVIDER=auto` 会让自动打码静默失效**：
   `auto` 被当成平台名往下传 → 被判"未知平台"。
   → `auto_captcha_provider()` 显式把 `auto` 与"未配置"等价处理。

### 其他实现要点
- 取图优先级：**img 的 src 直连下载 > 元素截图**。截图可能把防自动化水印/马赛克截进去，

### ⚠️ 由此暴露的一个真 bug：平台的 code 是**字符串**
云码返回 `"code":"10003"`（字符串），而代码原来是 `if code != 10000`（整数比较）→
- **成功时服务端回 `"10000"`，`"10000" != 10000` 恒真 → 成功也被判成失败**（功能全废）
- `"10003" in {10002,10003,10004}` 为假 → 余额/权限类**致命错误漏掉 fatal 判定**，徒劳重试
修复：新增 `_as_int()` 归一后再比较；`_payload_field()` 兼容 data 的三种形态
（dict / **空 list**（云码失败态）/ 标量）。图鉴的 `-1` 也按实测写进 `_FATAL_CODES`。
→ **教训：桩服务器用整数码写了测试，导致"假通过"。凡是"平台返回什么格式"的假设，
   都必须用真实端点（假凭据即可）验证一遍。**

## 问题：落点要不要加随机偏移？会不会被检测到？（15:4x）

### 结论：**落点不需要加随机偏移**；但"过于规整"的问题确实存在，只是**不在落点、在轨迹**
理由：
1. 服务端看到的是**轨迹 + 最终位移**，它不知道我们的"理想落点"是什么，
   所以"落点等于某个由识别角度算出的值"这件事**本身不可检测**（跨会话更不可比）。
2. 落点**本来就天然变化**：每张验证码图不同、云码识别结果也有几度波动
   （实测误差 -9/+3/0），所以同一落点不会重复出现。
3. 加人为偏移只会**吃掉有限的容差余量**：平台识别本身有 ±4~9° 误差，
   再叠加随机偏移会显著提高失败率 —— 属于"为了不可检测的东西牺牲真实通过率"。
→ 新增配置 `CAPTCHA_LANDING_JITTER_PX`（默认 **0**），并在 config/.env.example 写清"不建议开"。
  真要试验建议 ≤1.5px(≈2°)。

### 但审计出 3 处真正的"规整特征"（都在 enrichers/aiqicha.py，已修）
1. **落点 y 完全没有抖动**：中间点都是 `y0 ± 1px`，唯独最后一点恒为 `y0`
   → 一个"完美水平终点"的硬特征。**这是最干净的一处破绽。**
2. **探测点恒在目标的 50%、停顿恒为 0.35s** → 每次都"在相对同一位置冻结同一时长"。
3. **过冲模式恒定**：永远"冲过头 3~7px 再回正"，从不"差一点再补"。

修法：
- 探测比例改 `uniform(0.32, 0.62)`、停顿改 `uniform(0.22, 0.50)`；
  且**目标 <30px 时直接不探测**（几何误差折算到角度 <1°，不值得暴露一次中途停顿）。
- 主段改为**两种模式随机**：35% 概率"差一点停下 → 停顿 → 向前补"，
  否则"冲过头再回正"。
- 落点后加 1~2 次微调（真人不会一步到位后僵住）；**末点也带 ±1.4px 纵向抖动**。
- 轨迹纵向抖动 ±1px → ±1.6px（±1px 经坐标取整后只剩 2 种取值，显得"贴着一根水平线拖"）。

## 独立站联系方式（enrichers/website.py）修复 + 全量评估（17:2x~17:4x）

### 上一轮已修（403 误当首页 / UUID 假号 / 1688 slug / 手机号截断）
- `_fetch_html` 不看状态码 → 403 错误页(199B) 被当首页 → 改为 `status_code >= 400` 返回 `alive=False`。
- 座机正则收紧：本地号必须连续 7~8 位、区号与本地号间**必须有分隔符**。
- 手机号与座机正则重叠时跳过（否则 `0086-15913797691` 被截断成 `0086-15913797`）。

### 本轮全量评估（33 个独立站）新暴露并修掉的 3 个问题
1. **区号前导 0 丢失**：`86-20-31477658` 输出成 `20-31477658`（不存在的号码）。
2. **境外号被当国内座机，且被截断**：`+44 7354893854` → `44-73548938`（**半截号**，比留空更糟）；
   `+65 90656597`（新加坡）→ `65-90656597`。
3. **`tel:` 链接完全没利用**：`href="tel:447354893854"` 这类最可靠的来源一个都没取。

### 解法：新增 `_canon_phone()` 统一归一化 + `taken` 区间去重
- 提取顺序改为：**`tel:` 链接 → 境外号(整串) → 手机号 → 座机 → 400/800**，
  每条规则命中后登记文本区间，后续规则**重叠即跳过**，杜绝"半截号 + 重复号"。
- 境外号（`(?:+|00)` 且非 86）**整串保留**输出 `+447354893854`；86 开头则剥掉走国内逻辑。
- 国内座机统一成 `0区号-本地号`；2 位区号用 `CN_AREA2={10,20,21,22,23,24,25,27,28,29}` 白名单
  （**这条白名单正是把 65/44 这类国家码挡在门外的关键**），3 位区号要求首字符 3~9。
- 区号切分**不能**用 `0(\d{2,3})(\d{7,8})` 一把梭：贪心会把 `02031477658` 拆成 203+1477658；
  改为按 (3,2) 两种切法逐个试，取第一个区号真实存在的。
- 三段式且每段 ≤4 位（`010-2019-1688`）判为 ID/日期，只在 `0` 开头分支拦截（不误伤 `132-0200-7108`）。
- `tel:` 属性值**可能含空格**（`tel:0086 15913797691`），正则只能用 `[^"'>`]+`，不能用 `\s` 排除。
