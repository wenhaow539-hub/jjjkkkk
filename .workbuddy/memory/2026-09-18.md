# 2026-09-18 工作日志

## 双浏览器 + 4 账号（单进程内并行）—— 已实现

用户口径（四条，都已确认）：
1. **单进程内双浏览器**（不是双进程 —— 双进程会让两个进程同时写 xlsx/seen_hashes.txt 而损坏数据）
2. **两条流各自完整跑现在这套流程**（GS采集→独立站→LLM→hybrid补全→落盘→写指纹）
3. **4 个账号** = 浏览器 A（天眼查1+爱企查1）/ 浏览器 B（天眼查2+爱企查2）
4. **A 本机直连、B 走 HTTP 代理**；代理地址暂时没有 → 只做能力 + 预留参数，默认空 = 直连
5. 关键词：**同一关键词分奇偶页**（A 扫 1/3/5…、B 扫 2/4/6…）
6. `-n 120` = **每条流各自 120**（合计约 240）—— 这个选择让方案大幅简化，不需要共享额度分配器
7. 双流**默认开**（NUM_STREAMS 默认 2）

## 架构

```
run_dual_pipeline()                    ← 新外壳
  ├─ 顺序预启动两台（消除并发抢端口的竞态）
  ├─ 端口唯一性校验（两台落同一端口 = 双流退化，必须报出来）
  ├─ 登录态检查（B 没标记就提示 + 等，超时只跳过 B）
  ├─ excel_lock = asyncio.Lock()       ← 两流共享
  └─ asyncio.gather(run_pipeline(ctx=A), run_pipeline(ctx=B))
```
`run_pipeline` 新增 `stream_ctx` / `profile`，**默认 None ⇒ 单流路径与改造前逐字节一致**。

## 两个隐藏 bug（都修了）

### 1. `pipeline.py:754` 的 `ensure_chrome_running` 漏传 `profile_dir`
原来只传 `port`，于是补全阶段永远退回默认目录 `./chrome_debug_profile` →
**B 会用 A 的 profile（= A 的登录态）且不报任何错**。现已补 `profile_dir` / `proxy` / `reuse_nearby`。

### 2. `core/browser.py` 的"复用邻近端口"（我的判断被修正了）
⚠️ **我原本的说法是错的**：附近扫描是 `range(port+1, port+11)`，**只向上扫**，
所以"请求 9223 会被错认成 9222"不成立（9222 不在范围内）。
真实会踩的场景是：① B 的端口**低于** A（如 BROWSER_B_PORT=9220）；
② A 因 9222 被非 DevTools 占用而自动改到 9223，而 B 也配 9223。
修法：给非主浏览器传 `reuse_nearby=False`（不做邻近扫描），**并**在 `run_dual_pipeline`
里做端口唯一性校验（真正的兜底）。

## 11:00 「浏览器又死了会怎样」的核查 —— 修掉端口回写 bug + 加采集中途自愈

## 11:10 多机部署的风险核实（用户问：部署到公司多台电脑、同一个公司 IP 会不会被封）

**核实到的三个硬事实（改造前必看）**：
1. `utils/dedup.py` 的 `HashDeduplicator` 用的是 `threading.Lock()` → **只在进程内有效**。
   跨机器（跨进程）**完全没有锁**。共享盘上两个进程同时 `_rewrite()`（临时文件 + `os.replace`）
   → 原子替换不会损坏文件，但**一方记录会被覆盖** → 被判"没见过" → 重复采集。
2. `export_leads_to_excel` 的串行化是 `asyncio.Lock`（`pipeline.py` 的 `StreamContext.excel_lock`）
   → 同样**只在单进程内有效**。多机写同一个 xlsx（read-modify-write）→ **静默丢行**（核心数据！）。
3. `main.py` 的 CLI **没有暴露 `--lane-offset/--lane-stride`** → 当前**无法**指定"这台机器扫第几页"，
   多机只能靠关键词/地区手动分任务。
   （`BrowserProfile.lane_offset/lane_stride` 只在进程内按 `NUM_STREAMS` 自动生成。）

**结论口径（已答复用户）**：
- 风控上：**机器数不改变风控本质，总量才改变**。N 台机器若每台都跑满 → 总量 ×N 才是危险源。
  正确做法是**总量固定、按机器切分**。
- 天眼查/爱企查：封 IP 多半是**临时**（验证码墙/限流数小时~数天），永久封家宽/企业 IP 概率低。
- 环球资源（国外站）风险更高：429/403 → 封 IP，且批量抓 B2B 供应商名录可能触及平台 ToS。
- **比风控更紧迫的是数据层**：多机共用同一份指纹库/报表是**必然损坏**（不是概率）。
- 多机场景下**每台跑单流（NUM_STREAMS=1）比双流更合理** —— 同 IP 下双流拿不到 IP 分摊收益，
  只增加密度；多机应该"每台单流 + 各扫不同车道"。
- 部署注意：profile 目录**不能跨机器拷贝后同时运行**（`SingletonLock` 冲突）；
  每台需各自 `--login-browser`；`.env` 各自独立。

### 天眼查与爱企查的一处本质差异（写进 docstring 了）

爱企查是页内 overlay。后果：天眼查**过码成功后正常会回跳到 `from` 指定的原页面**，
所以"页面还停在拦截 URL 上"就等价于"又弹了新码"——这也正是旧实现误判"已放行"的根源。
