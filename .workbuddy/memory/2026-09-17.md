### 用户报障

### 实际根因（与用户判断不同：这行**压根没被查过**）
只读抓了一次详情页，`_parse_detail` 返回：
```
registered_company = 'SHENZHEN XINLIKE SILICONE PRODUCT CO., LIMITED'   ← 纯英文！
registered_address = 'UNIT 917B, 9/F., TOWER A, NEW MANDARIN PLAZA, NO. 14 SCIENCE MUSEUM ROAD, TSIMSHATSUI, KOWLOON, HONG KONG'
official_website   = 'http://www.sxsilicone.com'
```
**香港离岸主体，GS 的「Registered Company Name」字段就是英文**。于是链条断成三截：
1. 我 9-16 加的「无中文名剔除」只判了 **非空**，没判 **是否含中文** → 英文名蒙混过关；
2. `_search_target()` 优先返回 GS 名（英文）→ `needing` 的 `has_chinese()` 过滤判假
   → **整家被跳过工商补全**（所以日志里"查无此企业 0"，它根本没进队列）；
3. Excel 的「公司中文名」列 = `enrich.registered_company or eval.clean_company_name or lead.registered_company`，
   **会回退到 LLM 译名** → 显示成中文，看起来一切正常。
→ 结果：`数据来源` 空、工商字段全空的废行，且日志完全看不出异常。

### ★ 核心风险：两家 enricher 对"没有数据"的处理**刚好相反**
```
爱企查：占位符 → 空串        （aiqicha.PLACEHOLDER_PREFIXES，9-16 加的能力）
天眼查：空值   → "未公开"/"-" （_clean_capital()/_clean_insured()，把"没有"写成了"有"）
```
不统一拦掉会同时踩三个坑（同一个根因）：
1. 切天眼查后表里填满 `未公开` / `-` 伪值；
2. 今天刚做的「工商字段全空则不入库」门槛**静默失效**（伪值非空 ⇒ 判成有数据）；
3. `_classify_result()` **恒判 ok**（`info["registered_capital"]="未公开"` 是 truthy）
   ⇒ 「站内查无此企业」永远不会出现，日志里 `查无 0` 会变成常态假象。

**修法：在 pipeline 层（不分数据源）统一归一**
```python
PLACEHOLDER_EXACT = {"-","--","—","/","无","暂无","未公开","未公布","未披露","未公示",
                     "无数据","null","none","n/a","na","登录","查看","详情"}
PLACEHOLDER_PREFIXES = ("暂无","未公开","未公布","未披露","未公示","无数据")
_real_value(value) -> str      # 占位符一律返回 ""
```
应用点：`_apply_tianyancha`（全部取值）、`_apply_aiqicha`（再兜一层）、
`_classify_result`、`_business_result_empty`。

## 天眼查「两段式点选」验证码接入（10:2x~）

### 验证码形态（用户截图实测）
```
第 1 段：tianyancha.com/sorry/captcha?from=%2Fcompany%2F2323333871&token=1789611538649-...
        页面中央一个按钮「点击按钮开始验证」
第 2 段：弹窗「请在下图依次点击」+ 顶部三个箭头图标（↑ → ↘）+ 下方彩色图形
        （橙星/粉花/蓝人/紫鸟），左下角有刷新图标，底部「确定」
```
⚠️ 拦截 URL **不含 "verify" 字样**，而原 `_handle_captcha_if_needed` 只查
`sec.tianyancha.com`/`verify` ⇒ **会漏判**。已补 `/sorry/captcha`、`/captcha`。

### 方案：云码 type=30009「通用任意点选1~4个坐标」
- **人工识别接口**（真人看图给坐标），**0.025 元/次**，比旋转类型贵约 10 倍
- 文档硬性限制：**只支持单图、不支持额外传参 ⇒ 规则必须画在图上**
- 返回 `data.data` = "指定的顺序坐标"
- 状态码同样是**字符串**（`"10000"`），复用 `_as_int()`

### ⚠️ 最大的不确定性（已如实告知用户）
天眼查的提示是**箭头图标**而非文字，打码员要自己推断"箭头方向 ↔ 哪个图形"的对应关系。
正确率**不会**像旋转验证码那样稳。所以第一步必须**先单独实测**，别直接接进流水线。

### 实施（4 个文件）
1. `config.py`：新增 `YUNMA_POINT_TYPE`（默认 `30009`）；`captcha_status()` 同时报旋转/点选两个 type。
2. `enrichers/captcha_solver.py`
   - `_parse_points()`：多格式解析（`x,y|x,y` / JSON 数组 / `["x,y",...]` / 带序号括号 / 连续逗号 / 空格）
     ——**严格保持平台给的顺序**（点选的全部意义在顺序，排序即答错）；解析不出来就抛错，
     绝不"猜"坐标。任何格式都解析不到时**不做兜底猜测**。
   - `_Provider.supports_points`（仅云码 True）；`YunmaProvider.point_type` 与 `type_code` **分开存**；
     抽出 `_post()` 复用（`solve_rotate` 也改走它，行为不变）。
   - `CaptchaSolver.solve_points()`：**独立实现**而不复用 rotate 的循环 ——
     旋转那条链路是已在真实站点验证过的，不为复用去动它。
   - CLI 新增 `--points <截图>`：不开浏览器、不跑流水线就能验证平台认不认得这种图。
3. `enrichers/tianyancha.py`
   - `__init__(captcha_mode, captcha_provider, captcha_wait)` + `_get_solver()` + `_resolve_wait()`，
     与爱企查语义对齐（auto/manual/off）。
   - `_captcha_present()`：URL 线索 + 元素双判。
   - `_handle_captcha_if_needed()` 改为**返回 bool**：auto 先试自动过码 → 失败转人工等待 → 放弃；
     `_manual_wait_captcha()` 可配置时长且**每 20s 打进度**。
   - `_auto_solve_captcha()`：点开始按钮 → 等弹窗 → 定位弹窗 → 截图 → 云码 → 按序点击 → 点确定 → 等放行。
     弹窗定位用 **JS 取"含提示文字 + 图片"的最小容器**并打 `data-wb-captcha` 标记，
     再拿它做 `bounding_box()` / `screenshot()`（**文本匹配而非 class，站点改版不会全废**）。
   - `_png_size()`：从 PNG 的 IHDR 读宽高（**venv 没有 PIL**）。
     截图坐标→页面坐标必须用真实像素尺寸换算（Playwright 截图按设备像素、鼠标点击按 CSS 像素，
     差一个 dpr 就点偏），不能假设 dpr。
   - 点击抖动刻意压到 ±1px：点选图形命中区小，为防检测牺牲命中率是亏本（同旋转落点不加偏移的判断）。

### ★ 顺手堵掉一个会**误删数据**的隐患

## ★★ 天眼查点选验证码真实跑通（11:15~，一次成功）

### 背景
用户自己搜了 50~60 条都没触发验证码，要求我写脚本触发。
→ 写了 `tests/trigger_tyc_captcha.py`（手动运行的取证工具，**故意不带 test_ 前缀**，
  `pytest tests/` 不会收集它）。

### 脚本的三条铁律（写进了文件头，源自 9-16 "一直在刷新" 的教训）
1. **出现即停** —— 一旦检测到验证码立刻终止所有导航（上一版就是带着
   "没检测到就继续下一家"的逻辑跑批量，表现为"一直在刷新验证码"）。
2. **先看现场** —— 浏览器里若已有验证码页，**一步都不导航**，直接取证。
3. **一轮一查且等渲染** —— 每次 goto 后先 sleep（默认 2s）再查；
   控件异步渲染，查太早必漏（这正是上一版"80 家跑完仍未复现"的原因）。
另有 `--rounds/--settle/--interval/--no-click/--close` 可调，取证后**默认保留标签页**。

### 触发结果
第 **7** 轮、**进详情页**时命中（前 6 轮搜索页 + 详情页都正常）。
捕获 URL：`tianyancha.com/sorry/captcha?from=%2Fcompany%2F2317992732&token=...`

**推测用户搜 50~60 条没触发的关键**：他大概只在**搜索列表页**搜，
而风控点在**详情页**（两次实测的拦截 URL 都是 `from=/company/<id>`）。
→ 脚本每轮是「搜索 → 点第一个结果**进详情页**」，所以第 7 轮就中。

```
**打消了最大的顾虑**：提示是**箭头图标**（↙ ↘ ↑）而非文字，原本担心打码员无法推断
"箭头方向 ↔ 图形朝向"的对应 —— 实测 3 个坐标全中，人工打码能正确理解这种语义。

### 实测得到的 4 条工程结论（已写进 `_auto_solve_captcha` 的 docstring）
1. 通过后**自动回跳**到 `from` 指定的原页面 ⇒ 调用方**不需要重新 goto**，
   后续 `wait_for_selector('table...')` 直接等工商表格即可（现有流程天然适配）。
2. 截图尺寸可能与容器尺寸**差 1px**（341 vs 340）⇒ 坐标换算必须用**真实图片宽高**
   （`_png_size` 读 IHDR），不能假设等于容器尺寸。这个设计选对了。
3. "含提示文字 + 图片的**最小**容器"定位策略**精准命中**弹窗本体
   （rect 与截图尺寸完全一致，且候选只有 1 个）。
4. 同一账号下云码返回的坐标每次不同（图片每次刷新）⇒ 不存在"同答案复用"。

## 拟人鼠标改造 + 由此暴露的选择器 bug（11:2x）

### 用户质疑（两条都成立）
> 「点第一个按钮有没有模拟人工鼠标移动点击，第二个图形验证码有没有模拟人工鼠标移动点击和
>   是否每次点击都在所需要点的图像固定位置」

审查结论：
```
第一段按钮: locator.click()  → 鼠标**瞬移**到元素几何中心、零中间点、down/up 间隔 0 —— 完全没拟人
第二段点选: mouse.move(steps=4~9) → 有中间点，但是**直线匀速**插值（无曲率、无加减速）
           落点 = 云码坐标 ± 1px  → 基本等于"每次都精确钉在图形几何中心"
           down()/up() 之间零延迟 → 按压时长为 0
```

### ★ 纠正一个我此前写错的判断
我原来注释写"点选抖动压到 ±1px，与旋转验证码落点不加偏移是同一个判断" —— **这是错的**：
- **旋转**：落点是滑块位移，服务端**不知道**"理想落点"，且识别误差本身让落点天然变化 → 加偏移纯吃容差余量，默认 0 是对的。
- **点选**：服务端**知道每个图形的确切位置** → "永远钉在几何中心"是**可统计检测**的自动化特征。必须加偏移。

### 实施
1. `_human_path()`：三次贝塞尔 + easeInOut 变速。两个控制点在路径 1/3、2/3 处
   沿**法向**随机外凸（距离的 6%~20%，方向随机）→ 曲率来源；采样点数随距离变化。
2. `_human_move()`：逐步 `mouse.move(x, y)`（**不带 steps**，自己插值），步间 4~18ms 随机。
   起点懒初始化为视口内随机点（不是 (0,0) 这种不可能位置）。
3. `_human_click()`：移动 → 到位停顿 40~160ms → `down()` → **停留 50~130ms** → `up()`。
4. `_human_click_locator()`：落点取元素框内随机（四周留 15% 边距），**不是几何中心**。
5. `_jitter()`：点选落点二维正态偏移，σ 取 `CAPTCHA_POINT_JITTER_PX`（默认 **3.0px**），
   拒绝采样截断到 2σ=6px。依据：蝴蝶图形约 35~45px 宽（半径 ~20px），6px 仍稳在命中区内。
6. 点击间隔 `0.30~0.75` → `0.45~1.30`（真人点完一个要看一眼再移过去）。
7. 三处点击全部改走 `_human_click_locator`：开始按钮 / 三个图形 / 确定按钮。

### ★★ 拟人化改动当场暴露了一个**潜藏的选择器 bug**（旧代码靠运气掩盖）
改成随机落点后，第一次实测**第二段弹窗没出现**。只读查现场发现：
```
含「点击按钮开始验证」文案的元素共 9 个；文档顺序第一个（= div:has-text(...).first 命中）
  DIV.container                rect=[0, 86, 929, 407]    ← 占视口一大半！
真正的按钮
  DIV.geetest_tips_wrap_xxx    rect=[411, 288, 112, 22]
```
`div:has-text()` 匹配所有**包含**文案的元素，`.first` 取文档顺序最靠前 = **最外层祖先容器**。
旧实现 `loc.click()` 点容器几何中心 (464,289)，**恰好**落在按钮区域内 → 看起来一直正常，
**纯属运气**；一改成随机落点就必然点空。

**修法两层**：
1. 新增 `_FIND_START_BTN_JS`：要求 innerText **精确等于**文案、面积 **< 40% 视口**，
   在合格者里取**面积最小**的（= 真按钮本体），打 `data-wb-startbtn` 标记后再拟人点击。
   （精确匹配失败时退化为"包含"匹配，但同样带 40% 视口上限。）
2. `_human_click_locator()` 增加**尺寸合理性检查**：命中元素 ≥ 视口 60% 就判定选错、
   打 WARNING 并**放弃点击**，不再猜。阈值取 60%（不是 50%）是因为验证码弹窗本身约
   340×385，在小窗口下可能接近视口一半。

### 验证（实测两次通过 + 离线 61 项）
```

`tests/test_tianyancha_captcha.py` 扩到 **61 项**，新增 F 组（轨迹曲率/变速/终点精确、

### ★ 根因①：「全新关键词」≠「全新公司」
指纹库是**按公司名**存的（与关键词无关）。环球资源「中国广东 + 近5年」这个池子在不同类目间
**高度重叠**（截图里很多卡片 Business Type = Trading Company，什么都做）。
数据库当前 **3218 条指纹**，所以一页 20 家里有 65%~100% 是老面孔 → 每页只能贡献 0~7 家新公司。

### ★ 根因②：选择器每页命中 60 个 a 元素，只有 20 个是真实公司名
每张卡片产生 **3 个**匹配元素：
```
① 公司名链接        ← 有用
② 空文本的 a        ← inner_text 为空（图标/整卡链接）
③ 描述文案链接      ← "We are professional at designing and producing..."
                      "Security Equipment Supplier with 16 Years of..."
                      "Specializing in wireless accessories since 2015..."
```
②③ 占 2/3，被 `is_valid_company_name` 白名单**正确拦掉**（这是好事，说明白名单在干活）。
但看日志/统计时容易被"命中 60 个候选"误导，以为丢了很多。

### 根因③：`DEFAULT_LIMIT = 10`（main.py:42）
不显式传 `-n` 时默认只采 10 家 —— 直接解释了"有时候甚至低于 10 个"。

### 根因④（今天新增的门槛，会减量）
`🧹 [入库前过滤]` 日志显示每轮剔 1~2 家：无中文工商名剔除 + 工商库查不到剔除。

### ⚠️ 需要提醒用户的隐患（重要）
```
指纹库 3218 条  vs  表格 286 行   →  2900+ 家「采过但不在表里」
```
而指纹是**不可逆的**：一家被采到 → 因无中文名/工商查不到被剔除 → **指纹已写 → 以后永远采不到**。
叠加用户 9-17 定的"无中文名直接删 + 保留指纹"，这个消耗是**永久性**的。
**结论：池子会越采越小，每页新面孔占比会持续下降** —— 这是结构性问题，不是 bug。

### 其他确认
- 翻页补偿**有效**（battery 第 3 页 60% 是新的），所以 `-n 20` 理论上 3 页内能凑够。
  用户若"只能抓到 10 几个"，更可能是 (a) 用了默认 `-n 10`、(b) 看的是单页产出、
  或 (c) 被④的门槛减去了一部分。
- **`supplier_location` 固定为 `China-Guangdong`**：`scrape()` 的签名有这个参数，
  但 pipeline 调用时没传 → 池子被锁在广东。**这是最容易打开的扩量口子**（浙江/江苏/福建）。
  已建议用户加 `--location` 参数，尚未实施。

1. 换**类目差异大**的关键词（电池 vs 手机壳重叠小）
2. 换**地区**（需要加 CLI 参数，未做）
3. 用诊断脚本先探一页新鲜度，再决定跑哪个词

- 对**已在报表里**的公司：会被重采，`added_count` 不算新增（旧行优先，行不会丢）→ 浪费配额
- 对**曾被剔除**的公司：能重新采到并入库 → **净增益**（实测这批 20 家全属此类）

### 顺带确认的两个安全点
1. 一家重采后若无中文名 → 本轮 `records` 里被剔除 → **不入 `new_df`，但旧行仍在 `old_df`**，
   合并后保留 ⇒ **不会丢行**（exporter 是合并而非覆盖）。
2. 重采已在表里的公司**不会**触发 `_recheck_legacy_missing_name` 的删除

**"一页 20 家只抓到 10 几个"的唯一原因就是指纹库**（65%~100% 老面孔），
候选/详情/工商补全三关实测都是干净的（100%/95%/100%）。

## 指纹库逻辑审计（11:54，用户问"现在的指纹库的逻辑是什么"）

### 存储
`seen_hashes.txt`：纯文本，**每行一个 32 位 md5**，只增不删（**代码里没有任何删除接口**，
只能人工编辑文件）。当前 101 条（用户 11:53 跑了一轮后重建的）。

### 哈希规则（`utils/dedup.py::get_company_hash`）
```python
clean_str = re.sub(r'[\s\W_]+', '', name.lower())   # 去空白/标点/下划线 + 小写
return md5(clean_str) if len(clean_str) >= 3 else ""
```
**返回空哈希 = 完全不参与去重**（`is_seen` 恒 False、`add` 恒 False）的三种情况：
1. 空 / 非字符串
2. `is_url_string()` 为真（含 `http://` `https://` `//` `globalsources.com` `www.`）
3. 归一化后不足 3 字符

### ★ 实测到的归一化漏洞（同一家会被算成多家 → 指纹数虚高）
```
'SHENZHEN XINLIKE SILICONE PRODUCT CO., LIMITED'  -> f1289b9dddd0ddf0
'Shenzhen Xinlike Silicone Product Co.,Ltd'       -> 3452dadbb46b0677   ← 不同！
'深圳市鑫利科硅胶制品有限公司'                        -> 0b38aec7f2227a77   ← 又一条
```
**根因：`Limited` 与 `Ltd` 不归一**（"limited" ≠ "ltd"）。加大小写/标点无关，但缩写不认。
→ 同一家公司很容易占 **2~4 条**指纹（英文名写法差异 + 英文名/中文名各一条）。
→ 这解释了"3218 条指纹"对应的公司数远少于 3218。

### ★★ 读写时机不对称（最反直觉、也是"永久消耗"的机制）
```
读：候选阶段 `scrape()` → is_seen(卡片英文名)  → 命中就跳过，未命中才抓详情
写：详情阶段 `process_item()` → add()          → **不管这家后续是否入库**
```
写入共 **3 处**（每家最多 3 条）：
```python
dedup.add(s["company"])                    # 英文名
dedup.add(detail["registered_company"])    # 中文工商名
dedup.add(name)                            # 9-17 我加的「同轮重爬」回填
```
⇒ **写入早于入库判定**：一家被采到 → 指纹已写 → 随后因缺中文名/工商查不到被剔除 → **永久消失**。
这就是"采得越多、每页新面孔越少"的机制来源。

### 两个附带发现
- **中文名那条指纹实际上永远命中不了**：候选阶段只拿得到**卡片英文名**，
  拿不到中文名 ⇒ `add(中文名)` 基本是无效写入（除非某关键词的卡片 title 恰好写中文名）。
- **单例只在 import 时加载一次**：`dedup = HashDeduplicator()` 是模块级对象，
  长驻进程内**不会感知文件的外部改动**（改完文件必须重启进程）。

### 共用一个文件的三个写入方
`crawlers/globalsources.py`（--pipeline 路径）、`adapters/globalsources.py`（main.py 路径 1）、
`crawlers/aicaigou.py`（爱采购）。**两条采集路径共用同一份指纹库**，互删互跳。

## 【GS 翻页进度跨批记忆】已实现

用户看了 ② 的说明后问「能不能加一个记住当前页数」→ 确认指的是
**GS 列表翻页进度**（不是存量复核、也不是整轮断点续跑）。

### 动因
分批跑时每批 `scrape()` 都从 `pageNum=1` 重扫：已进指纹库的家会被 `dedup.is_seen`
跳过，但**页面本身仍要重新加载 + 滚动 3 次**（2~3s/页）。4 批下来纯属白烧。

### 改动（`crawlers/globalsources.py`）
- 新增 `__init__` + 实例属性 `_page_cursor: dict[str, int]`
- 新增 `_cursor_key()` / `_cursor_get()` / `_cursor_put()` / `reset_page_cursor()`
- `MAX_SEARCH_PAGES = 25` 从 `scrape()` 的局部变量提为类常量（单一出处）
- `scrape()`：进入时读起始页并打印「承接上批进度，从第 N 页继续」；
  翻页循环结束后 `_cursor_put(ckey, page_num)` 记录

### ⚠️ 两个关键判断（都写进注释了）
1. **记的是「当前页」而不是「下一页」**。命中 `max_count` 时内层 `break` 提前退出，
   本页**没被吃干净** —— 记成下一页会永久漏掉本页剩余候选。
   所以下一批重扫该页，靠指纹去重跳掉已入库的、把剩下的接上。
2. **页面 `query_selector_all` 返回空时不前进游标** → 下批重试。
   因为"空"既可能是真翻到底、也可能是渲染失败/被拦，宁可重扫不可漏采；

## 【诊断】"HTTPX 异步提取 30 家"为什么卡挺久（只读，未改代码）

用户问：「这里不是异步的吗，怎么会在这里卡挺久的」。结论：**异步 ≠ 快，瓶颈在限速器。**

### 微实验（隔离 `utils/ratelimit.AsyncRateLimiter` 实测）
12 个请求、并发上限 4 → **耗时 12.6s**，相邻启动间隔 `[1.03, 1.6, 1.31, 0.81, 1.12, 0.82, 0.99, 1.01, 1.44, 1.25, 1.18]`
→ 均值 1.14s/请求，**完全串行**。`asyncio.gather` + `Semaphore(4)` 的并发度只用来隐藏网络延迟，
**对吞吐零帮助**。

### 30 家的请求账
每家：profile + contact（并行发也要排队）+ home（任一为空时）+ contact 重试 + home 补抓
→ 实际 3~4 次/家 → **90~120 次请求** → 纯限速 **1.8~2.4 分钟**。

### 被限流的页面代价最大
`_fetch_html(retries=2)` 里 **`acquire()` 在重试循环内部** —— 每个 attempt 都重新占一个限速槽：
3 次限速槽 3.6s + 退避 `max(1.5,1.5*(a+1))` = 1.5+3.0 → **单页 ≈ 8.1s**。
30 个页面被打回就是 **+4 分钟**。
（最坏单页：3 × `client.get(timeout=15)` + 4.5s 退避 ≈ 50s）

### 为什么"看起来像卡死"
`asyncio.gather` 只在**全部完成后**打一行汇总，中间**没有任何输出**
（对比：天眼查每家都有日志）。

### 这个限速是故意的
`BaseCrawler.__init__` 注释：早期 concurrency=4 + 每家内部再并发 2 → 瞬时 8 个请求零间隔打向
同站 → 被限流/拒绝且失败被静默吞掉 → "整列字段空白且看不出原因"。限速是修那个问题加的。

### 可调方向（已告知用户，未实施）
- `min_interval` 1.2 → 0.6 可省一半时间，但风控风险上升
- **调大 `concurrency` 没用**（瓶颈是限速器，不是并发度）
- 给详情阶段加**逐家进度打印**：只改善体验，不改速度

### → 用户选择：min_interval 1.2 → 0.9（已实施）
| 文件 | 改动 |
|---|---|
| `config.py` | 新增 `DETAIL_RATE_MIN_INTERVAL`（默认 **0.9**）+ `DETAIL_RATE_JITTER`（0.35）+ `detail_rate_status()` |
| `core/base_crawler.py` | `import config`；限速器改为读 config（4 个爬虫共用），注释写明"它才是真正的瓶颈" |
| `crawlers/globalsources.py` | `import config`；「启动 HTTPX」那行**追加打印限速参数与本阶段预估耗时** |
| `.env.example` | 新增两项（可覆盖），并写明"再往下压反而更慢"的理由 |

**做成 config 项而非硬编码**：用户以后调数值不用再改代码。

实测（12 请求 / 并发 4）：`1.2 → 15.2s (1.26s/请求)` vs `0.9 → 9.6s (0.80s/请求)`；
30 家估算 1.8→1.4 分钟 / 2.4→1.8 分钟，**省 25%**。

测试：`test_batch_loop.py` 新增 [N] 8 项（含"N6 不再硬编码 1.2"的防回退断言）→ 该文件 **70 项**；
6 个文件合计 **322 项全过**。用户 `.env` 未设该项 → 走默认 0.9。

## 【修正】末批超采：目标 60 结果入了 84

## 【提速】异步预取：下一批的轻活与本批的工商补全并行

用户 17:5x 实跑 `-n 120`（5 批）后要求提速：「在爱企查开始的时候就开始候选入库…
然后停止等待爱企查查完，就直接给天眼查开始，实现异步」。

### 收益来源（关键洞察）
两家工商补全**最慢**，但时间几乎都花在**浏览器空转**上：
每家族 3~6s 冷却 + 每 17~20 家 45~60s 大休眠 + 验证码等待。
那期间浏览器闲着 —— 正好用来把**下一批**的「GS 采集 + 独立站 + LLM」跑掉。

### 拆分
原来 `_run_batch` 一整个串行，现拆成两段：
| 函数 | 内容 | 耗时特征 |
|---|---|---|
| `_prepare_batch()` → `records` | 采集 → 无中文名剔除 → 独立站 → LLM 质检 | **轻**，几乎不占补全链路 |
| `_finish_batch(records)` → added | 两家补全 → 工商空剔除 → 存量复核 → 落盘 → 兜底写指纹 | **重**，慢在浏览器等待 |

主循环：① 取本批 records（优先用 `pending` 预取结果）→ ② `asyncio.create_task(_prepare_batch(下一批))`
→ ③ `await _finish_batch(本批)` → ④ 收预取结果存进 `pending`。

**我按用户描述做了但把时机放宽了**：他说「爱企查开始时」，我改成「两家补全开始时」——
天眼查的 3~6s 冷却 + 45~60s 大休眠期间浏览器同样空转，早开始就多省。已在回复里说明。

### 三个必要防护
1. **GS 采集必须自建专用标签页**（原来用 `context.pages[0]` 复用）：
   并发时补全也有自己的页，复用 pages[0] 会让两者抢同一个 page 互相导航 → 必崩。
   同时 `page.close()` 收尾（否则一批积一个标签页）。
   为此把「翻页到顶」那处的 `return []` 改成压低 `max_search_pages`，否则会跳过关页。
2. **不无谓预取**：条件 `empty_streak == 0 and (ingested + take) < total_count`。
   没有第一条，最后一批永远多备一批；没有第二条，熔断边缘还浪费一次采集。
3. **预取批次被丢弃时回滚指纹**：目标已达成 → `_rollback_dropped_fingerprints`。
   候选阶段已写指纹，不撤就是"采了却没进报表"，下次被 is_seen 跳过 = 白丢。

### 接线
`run_pipeline(async_prefetch=True)` 默认开；`main.py --no-async-prefetch` 可关；
`run_mvp.py` 的 `ASYNC_PREFETCH = True`。关掉 = 退回严格串行（更稳，但慢）。

### 测试
`tests/test_batch_loop.py` 新增 [Q] 12 项 → 该文件 **88 项**；6 个文件共 **378 项全过**。
[Q1]/[Q2] 是核心断言：进入第 1 批补全时 scrape 调用次数 **2（开）vs 1（关）**
—— 直接证明"下一批的轻活在补全之前就并行铺开了"。

## 三个坑的复核与补漏（同日后续）

用户要求"堵这 3 个坑" → 核查发现**三处主体都已在代码里**，但 ②③ 各有一条路径没堵严：

### ② 多出来的预取必须退还（原实现只预取不截断）
预取时算 `prefetch_take` 用的 `ingested` 是**旧的**，可能大于本批实际需要的 `take`。
不截断就绕过「末批只补差额」：
```
批 4 开始还差 41 → 预取 30 家；批 4 实际入 26，累计 105/120 → 末批只需 15 家，
却把预取来的 30 家全吃下去 → 又超采 15 家（表头还写着"上限 15 家"）
```
修：消费 pretech 结果时 `if len(records) > take:` 截断多余部分 + 回滚其指纹。

### ③ 循环因子批次上限退出时的遗留（原实现只覆盖"目标达成"一条路径）
`max_batches` 用尽 / 熔断 break 后，`pending` 里还躺着一批"指纹已写、没进报表"的家。
修：循环体之后加收尾回滚。**注意 `prefetch.cancel()` 那条路径无法回滚**
（cancel 会丢掉 records），只能告警，已在日志里明说。

### 顺手修的统计口径
`scraped_total` 在挂预取时就 += 了，丢弃时要 -= 回来，否则收尾那句
「各批采集上限合计 N 家候选」会虚增 —— 用户就是靠这个数字判断有没有超采的。

### 测试基建的两个修正（值得记）
1. **`_NullLogger` 原来把日志全 `pass` 丢弃** → 无法断言关键输出（如"上限合计"）。
   改成静默记录到 `_NullLogger.LINES`，仍不刷屏。

   才没触发重写文件），既脆弱又无法断言 → 换成记录式替身 `_ROLLBACKS`。
